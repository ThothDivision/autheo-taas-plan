Compliance & security

Three promises: only eligible people can hold the asset, nobody but the owner can move it, and every decision leaves a tamper-evident trace. Autheo provides technology; regulated roles (custodian, venue operator, transfer agent) are meant to be held by licensed partners.

Who may hold an asset

  • Credentials. A trusted KYC provider signs a credential for a wallet, with claims: KYC, ACCREDITED, INSTITUTION, and a jurisdiction. Anyone can submit it to the on-chain credential registry; only the provider can revoke it; if the provider is distrusted, all its credentials stop counting at once. Built with a test provider key.
  • Asset rules. The issuer (or transfer agent) sets each asset's rule set: required claims, allowed jurisdictions, minimum size, holding limit, lock-up end, daily transfer window, and whether a live physical attestation is required. Only the token's owner can change it. Built
  • Physical truth. For physical assets, a Lumenco micro-optic security feature is scanned; only a fingerprint (hash) goes on-chain. If required, nothing mints or moves without a live attestation, and anyone can check a fresh scan against the record. Built with a test scanner key.

Transfer restrictions: the 12 checks

Every mint, transfer and burn runs these checks on-chain. The off-chain engine runs the same checks first so people see the reasons before signing.

CheckPlain meaning
amount_validThe amount is greater than zero
asset_activeThe asset is not paused
sender_credentialThe sender holds a credential that is not revoked or expired (not applied to a mint)
receiver_credentialThe receiver holds a credential that is not revoked or expired
receiver_eligibilityThe receiver has the required claims (e.g. accredited)
jurisdictionThe receiver's jurisdiction is allowed
minimum_sizeThe trade meets the minimum size
holding_limitThe receiver will not exceed the holding cap (the issuer is exempt)
lockupThe lock-up period has ended (the issuer is exempt)
transfer_windowIt is inside the allowed time window of the day
sender_balanceThe sender has enough
physical_attestationThe physical item has a live attestation, if required

A failed on-chain transfer reverts with a bitmask of the failed checks that decodes to the same names and reasons the API shows (ADR 0004).

Architecture decision records

ADRDecision in one line
0001Permissioned token with ERC-3643 semantics (every movement asks one shared compliance module); not the full T-REX suite until a partner needs it
0002Non-custodial: users sign EIP-712 orders, settlement goes maker to maker in one transaction, the DvP contract has no owner, services are read-only
0003Physical verification: per-item hash of a Lumenco scan, signed by a trusted attester, required by rule; a lost or disputed item freezes until re-attested
0004One rule model written twice (TypeScript and Solidity), tested against the same vectors; on-chain reverts decode to the same reasons
0005Tooling: TypeScript npm workspaces on Node 20+, Solidity + Foundry, OpenZeppelin, viem, MCP SDK
0006Agent authorization: optional Autheo delegation-chain request on the tools, verified offline; allow / escalate / block; agentRef in the order; signed receipts in the audit log

All six were accepted on 13 Oct 2026. The wider plan's open decisions (D-01 to D-13) and risk register are in the TaaS plan's Decisions and risks; the DEX plan's own risk list is Risk register (plan).
